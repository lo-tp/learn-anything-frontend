# Browsing is public, ownership is not

A Visitor — a person who has not signed in — can use the app. The site root is the public **Explore** feed, and a Session's generated deck (its public record) can be opened by address and browsed and answered by anyone; sign-in is required only where data is owned — a User's **History**, a Session's intake, and the review writes that attach to a Session. This reverses the earlier decision that every function of the app required sign-in: the edge used to verify the token and redirect anonymous visitors to a login page, and the glossary's sign-in-state entry said "every function of the app requires it." That gate is gone (#149), the public surfaces are open (#150/#151), and History keeps its own address at `/mine` (#148) — so browsing is public and ownership is not, by contract rather than by a redirect.

Considered and rejected: keeping the edge sign-in gate (it re-coupled every page to a login redirect and left the public surfaces unusable without credentials — exactly the behaviour this reverses); server-gating the personal surface, i.e. refusing `/mine` outright to an anonymous visitor (it would make History a hard 404 wall instead of letting the page render and the sign-in modal ask in place over it, and it puts the ownership boundary in the route rather than in the API); probing identity to label the chrome — swapping top-bar wording on the result of an identity probe (it couples shared chrome to a probe-and-branch for a difference a plain sign-in affordance already covers — an unsigned visitor simply sees no account menu and the sign-in entry point).

Consequences: no ownerless Sessions by contract — every Session is owned by a signed-in User (creating one requires sign-in), and the public Explore feed deliberately carries no owner identity, so "public" never means "ownerless"; a `401` is the only identity signal — `isSignedIn()` resolves the viewer's state solely from the `GET /auth/me` answer, where `401` means Visitor, and no other identity signal is read or stored client-side; and the session rides an HttpOnly cookie the client can never read — the API client sends `credentials: "include"` and never reads `document.cookie`, so the token stays out of the page's reach.
