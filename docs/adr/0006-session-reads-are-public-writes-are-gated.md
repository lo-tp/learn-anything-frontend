# Session reads are public; every write is gated

ADR-0004 decided that browsing is public and ownership is not, and the frontend was built to that contract — one Session address for both audiences (#151), the sign-in modal asking in place (#147). But the boundary was drawn in the wrong place: the backend kept a sign-in gate on the Session **reads**, and that gate only opened under `DEV_MODE`, so in production a Visitor's list was a capped public feed and a Visitor's deck was a 401 over a "not found" panel (#177). This amends ADR-0004 on that point: **the Session list, one Session's state, and its generated materials are public reads, answered identically whatever `DEV_MODE` says; every write — creating a Session, the intake, the plan, the review cards — still asks for a User.** Ownership begins at the write, not the read.

Considered and rejected: keeping a separate public list endpoint (`GET /explore/sessions`, #144) and uncapping it — it left two endpoints answering one question, with a server-side phase policy and a cap in one and a query parameter in the other, and a second generated client type for the same `SessionList`; the phase set was already duplicated in the frontend as `CONFIRMING_PHASES`. One list endpoint with one query removes the divergence rather than syncing it. Also rejected: capping the public list instead of removing the cap — the surfaces have no pager (#143), so a cap silently hides the oldest Sessions, which is the defect #177 reported. Also rejected: gating the reads at the edge — ADR-0004 already rejected putting the ownership boundary in a redirect, and it would break the deck addresses the app already links to.

Consequences: the list exposes every Session's goal text to anyone, and some goals are personal — owner identity stays absent from the payload (no email, display name, or user id), which is the weaker version of the exposure and the one #144 accepted; a `401` from a Session read is no longer a thing the app reacts to, so the sign-in modal now arrives only from a write or from the identity probe, and the `401`-to-modal path on the list views is a fallback rather than a normal flow; the Explore feed endpoint and its client function are gone, and the site root and `/mine` issue the same request (`GET /sessions?phase=…`) — the top-bar split ADR-0005 records is unchanged, and now rests on the label and on what the CTA opens for each audience, not on different content. If that split stops being wanted, it is a chrome decision, not an API one.
